/********Tut 21**************/
      1)CSS Specificity and Cascade
            1)Cascade Algorithm : 
                  The cascade algorithm has 4 distinct stages : 
                  1)Position and order of appearance : for use when same types of selectors in conflict
                  2)Specificity: for use when different types of selectors in conflict
                        Order of specificity is:
                        Inline Style > ID Selector > Class or Attribute Selector > Element Selector > Universal Selector

                        Tip : 
                        1)Use the least specific selectors more often to style your HTML. That way you can easily override specific styles when needed with more specific selectors. 
                        2)As a consequence of Tip 1), you should use !important v.very sparingly in your code (as it would make debugging difficult)
                        3)To calculate specificity, assign a value to each part of the selector:

                              -Universal Selector: 0
                              -Element selectors and pseudo-elements: 1
                              -Class selectors, attribute selectors, and pseudo-classes: 10
                              -ID selectors: 100
                              -Inline styles: 1000
                              -!important : 10,000
                        Then, add up the values of all the parts in the selector.

                  3)Origin
                  4)Importance: some CSS rules are weighted more heavily than others, especially with the " !important " rule type

                  Tip: There is NO " justify-items " in flex box 🙂
                  
            8)Shorthand to set "flex-direction" and "flex-wrap" :
                  flex-flow: <flex-direction> <flex-wrap>

            1)order (jitna zyada order utna baad me element aega, default order is 0)

                  You will tend to find a hierarchy here.

                  Run time environment - Everything you need to execute a program, but no tools to change it.

                  Build environment- Given some code written by someone, everything you need to compile it or otherwise prepare an executable that you put into a Run time environment.       🟨🟨JS callbacks and promises🟨🟨

      1)Asynchronous programming is implemented in JS (say for functions that may take a long time to return their output)
            (Ref: https://developer.mozilla.org/en-US/docs/Learn/JavaScript/Asynchronous/Introducing)
      2)callback functions : callback functions are passed as arguments to other functions and then executed inside this outer function to perform some action.
            Tip : 1)callback functions are used to implement Asynchronous programming (like executing a callback once a time taking Asynchronous task completes)
                  2)Poor use of callbacks can lead to "JS Pyramid of Doom" 💩 (see : https://matcha.fyi/pyramid-of-doom-javascript/)
      3)promise : used to prevent "JS Pyramid of Doom" 🛡️. Let's see in more detail
            1)What is a Promise? 
                 A)It is used to execute some code parallely in background in JS.
                  The promise then tells if that code was executed successfully or not.
                       (i) promise resolved : if that code was executed successfully
                       (ii)promise rejected : if that code was NOT executed successfully (i.e some error occurred)
                 B)This code (inside the promise) can be a synchronus code OR asynchronous code 
                 c)Basically promise is a task that i wish to get completed parallely in background.
                   🌳Practical use case:
                        Say u are running a synchronus code & in b/w you made a network call. Ab is network call se dhere-dhere 🐌 data aega. So i wouldn't want to freeze the entire webpage (and frustrate 😡 the user) while this is happenning. So i will handle the network call asynchronously & parallely in background using a promise. The promise will tell me if the network call was successfull or not in the end (i.e data aa paya ya kuch gdbd ho gyi). 

                        Note: 1) See "Event Loop" in JS from LB WebDev local saved Video "80. JS DOM Class - 1".
                              2) Note that LB only explains the traditional Event Loop i.e with only 1 queue (now called the Macrotask Queue). With ES6 and the introduction of promises, we have another queue: Microtask Queue.
                              3) So, the Event Loop now has 4 components:
                                    (i) Single Call Stack (Bcz JS is Single threaded so there is only 1 call Stack)
                                    (ii) The Browser (i.e WEB APIs)
                                    (iii) Macrotask Queue: for event-handlers and WEB API callbacks (like setTimeout's callback: after the times expires, this callback goes into the Macrotask Queue)
                                    (iv) Microtask Queue: for callbacks of .then(), .catch() and .finally() (+ other things)

                                    💙 Great Video that covers this "new" Event Loop: https://youtu.be/eiC58R16hb8?si=zovgIjFCS8Wwi6NO 

            2)Syntax of a making a promise (basically we will make a promise object using a call to constructor of its class):

                        let meraPromise = new Promise(function(resolve, reject){
                              //Any code to be run parallely
                        });

                        Ex:
                        //Synchronus code inside promise (To be run parallely)
                        let meraPromise1 = new Promise(function(resolve, reject){
                              console.log('I am inside Promise1');
                        });

                        Here, "meraPromise1" is a promise object. 😊😊
            
            3)A promise object has following properties:
                  1)state : pending, fullfilled OR rejected
                  2)result : 
                        (i)promise resolved : result is a value
                              -use "then()" method of promise object to work with value
                        (ii)promise rejected : result is an error
                              -use "catch()" / "then()" method of promise object to work with error

                              Tip: If your promise returns an error, u need to chain the then() & catch() methods, using them separately won't work bcz then() does not catch errors, so JS engine returns error ('ERR_UNHANDLED_REJECTION')

                                    ❌❌WRONG❌❌
                                    let p = new Promise(function(resolve, reject){
                                          reject("p rejected");
                                    })

                                    p.then((val)=>{
                                          console.log(val);
                                    })

                                    p.catch((err)=>{
                                          console.log(err);
                                    })

                                    ✅✅Correct✅✅
                                    let p = new Promise(function(resolve, reject){
                                          reject("p rejected");
                                    })

                                    p.then((val)=>{
                                          console.log(val);
                                    }).catch((err)=>{
                                          console.log(err);
                                    })

      Middlewares in Express.js
      
      🟩What is middleware?
      1)What is a web-server : We see a web server as a function that takes in a "request object" and outputs a "response object". So there is this "request-response cycle" : 

            1)request ayi
            ⬇
            2)Beech me web application (i.e server)  
            ⬇
            3)response gya

      2)Middleware is anything that is placed in between the request-response cycle.

            1)request ayi
            ⬇
            3)Beech me middleware : so before the request can reach the actual server logic, it is intercepted by the middleware(s)
            ⬇
            2)web application (i.e server)  
            ⬇
            3)response gya

            See "middleware1.jpg"

            So, Middleware is a request handler that allows you to intercept and manipulate requests before they reach route handlers.
            (See "server.js" for example)
      
      3)So, Middlewares are functions that have takes 3 objects:
            1)request object (req), 
            2)response object (res),  
            3)the next middleware function in the application’s request-response cycle. 

            A Middleware can perform the following tasks:
            - Execute any code.
            - Make changes to the request and the response objects.
            - End the request-response cycle.
            - Call the next middleware function in the stack.
      
      ⚠️Warning : If the current middleware function does not end the request-response cycle, it must call next() to pass control to the next middleware function. Otherwise, the request will be left hanging (the browser will forever show the loading icon - see EXAMPLE 4 in "server.js" )

      Syntax to write your own middleware function: 
                        app.use(<your own middleware function)
      
      4)To write middleware specific to a route (when you are using the "express.Router" class), write that middleware insdie the file that is handling that route (see "server2.js" and "routes" folder)

      5)Order matters in middleware. Say you have :
            app.use((req, res, next) => {
                  req.name = "Geetansh Bhardwaj"; 
                  next()
            })

            app.use((req, res, next) => {
                  req.name = "Soahm Sharma"; 
                  next()
            })


            So finally "req.name" will hold "Soahm Sharma". (Just like how flow works in simple JS code, bcz this is JS after all 😊)
      
      6)5 Types of middlewares : 
            1. Application-level middleware : when we write our own (like in "server.js" )
            2. Router-level middleware : middleware specific to a route (see point 4) )
            3. Error-handling middleware
            4. Built-in middleware : builtin in NodeJS
            5. Third-party middleware

            3)Pitfall 💀⚡ : Do not copy a prop into a "state". This violates "single source of truth" policy and leads to bugs
                  1)If a compnent receives a "prop" from it's parent and you can directly use that "prop" inside the child component, do that instead of storing the "prop" in a local "state" and then using that local "state" because "state" will persist during re-renders of that component and you will have mysterious bugs 🐛🐜
                  2)This is a classic case of copying props into local state -- which you usually do not want to do as it introduces a surface area for bugs, including the one you are seeing. If something is available as a prop -- what is the purpose of copying it into local state?
      
      2)Concept of IIFE (Immediately Invoked Function Expression)
            Say i am writing JSX and I have a button jisme "disabled" attribute hai. If i write "disabled = true" then the button will be disabled. Basically "disabled" expects a boolean. Say i don't want to directly supply a boolean but use a function that returns a boolean (In actual use case the function will return "true" or "false" based on some condition!). Ways to do this:
                  🟧Method 1 : define a JS function like usual.
                              
                        function disableBtn() {
                              return true;
                        }

                              disabled={disableBtn()} 
                        >

                  The following is ❌❌WRONG❌❌ : 
                        function disableBtn() {
                              return true;
                        }

                        <button
                              disabled={disableBtn} 
                        >

                        disabled={  (function disableBtn() {

                              } else {

                              }
                        })()}

            |       |-- Component1.jsx

            So just so you can use the state in the lowest component, `Component1.jsx`, you had to pass it into all other higher components.

                        </button>
                  </CountContext.Provider>
            </>

            Here, [] would contain those "dependencies" jinke change hone pe the Expensive Calculation would be redone. For ex:

                  const [stateX, setstateX] = useState(0);

/********************** TanStack Query/ React Query Starts *****************************/
      Basic Concepts of TanStack Query/ React Query ( https://youtu.be/mPaCnwpFvZY?si=uQacvy-FMr1xTpyR )

            0) TanStack Query/ React Query in a nutshell:
                  - It provides a hook that contains react state for: "data", "loading", "errors" etc. all in a single hook.
                  - Normally, you would make a "loading" state in react that would render a loading icon when your app is fetching data from the server. Then once the datahas been received, you would update the "loading" state to remove the loading icon. Let's say 15 minutes have passed, now the data no the server might be updated so you again set the "loading" state to true and refetch the data. 
                  - In addition to this, if the fetch fails, you have to retry.
                  - So, basically, this all is boilerplate code that needs to be repeated whenever your app is fetching data from a server.
                  - TanStack provides all of this builtin in a single hook.
            
            📒Note: More details and where to use Redux/ Context Provider instead:
                  🌍 Two Worlds of State

                  In frontend apps, you deal with two kinds of state:

                  1. UI / Client State
                        * Things that live only in the frontend.
                        * Examples: is a modal open, current page, dark mode, form input, cart before checkout.
                        * Best tools: React state, Context, Redux, Zustand, Jotai, etc.

                  2. Server State
                        * Data that comes from the backend and can change outside your app’s control.
                        * Examples: products list, user profile, comments, search results.

                        * Challenges:
                              * Needs fetching
                              * Can be stale (server updated elsewhere)
                              * Needs caching
                              * Needs sync across components
                              * Needs retries, pagination, optimistic updates


                  🧩 Where Context / Redux shine
                        * Great for client state (stuff entirely in frontend).
                        * You can use them for server state too, but then *you* must build:
                              * Fetching logic
                              * Error handling
                              * Loading states
                              * Caching & invalidation
                              * Retry/backoff logic
                              * Sync between tabs/focus

                  That becomes a **lot of boilerplate** → basically reinventing TanStack Query inside Redux/Context.

                  🚀 Where TanStack Query shines
                        * It’s specialized for server state.
                        * Gives you all the messy stuff for free:
                              * Data fetching & caching
                              * Auto refetch when data might be stale (window focus, tab refocus, time-based)
                              * Retry failed requests
                              * Invalidate queries after mutations (add/update/delete → auto refresh list)
                              * Pagination, infinite scroll
                              * DevTools for debugging

                  So you don’t have to write the plumbing — just say *“how to fetch this”*.

            1) useQuery Hook: this is the main hook provided by TanStack Query. From this, you get many things like:
                  - data : actual datat returned by your query
                  - isPending (Most suitable in most places): "true" if there is no data for the current query in the cache. 
                  - isFetching
                  - isLoading
                  - error : if the query errored out and could not fetch any data
                  - refetch etc...
                  
                  📙 How to use (See "FrontEnd/TanStackQuery/src/App_1_Intro.jsx") [Rename to "/App.jsx" to run it]:

                        const { data, isPending, refetch } = useQuery({
                              queryKey: ["todos"],
                              queryFn: getTodos,
                        });
                  
                  Here: (i) queryKey : this must be UNIQUE, this is how TanStack uniquely identifies this particular query in the entire app.
                        (ii) queryFn : The function that the query will use to request data.

                  See more (Official Docs: https://tanstack.com/query/latest/docs/framework/react/reference/useQuery )

            2)(See "FrontEnd/TanStackQuery/src/App_1_Intro.jsx") [Rename to "/App.jsx" to run it]) Suppose you have a React state variable "id" that stores which post’s comments your app is currently displaying. You would pass this "id" to your API like this:  
                  /comments?postId=${id}  

            Now, your queries are being cached by TanStack Query, so, it needs to know about this "id". Otherwise, it will treat different queries the same and cause problems. For example, these two queries must be treated as separate:  
                  /comments?postId=1  
                  /comments?postId=2  

            To handle this correctly, you need to tell TanStack Query that the query depends on the React state "id", so it can cache them accordingly:

                  const [id, setId] = useState(1);
                  const { data, isPending, refetch } = useQuery({
                        queryKey: ["todos", id],
                        queryFn: () => getTodos(id),
                  });
            
            3) How to handle multiple queries. (See "FrontEnd/TanStackQuery/src/App_3_MultipleQueries.jsx" )

      Advanced Topics of TanStack Query ( https://youtu.be/KkxPtimqaew?si=6mLJ_1hGQH3WzFfR )
      1) More options in useQuery hook:
            1)staleTime : The amount of time after which the cached data is considered "stale". Default is 0ms (immediately stale). 
                  Ex: Say you set it to 5 minutes for data with queryKey "K", this data will be fresh for 5 minutes after fetching. So, if a new request is made with this queryKey after say 10 minutes, TanStack will notice that we are beyond the staleTime and will refetch the data from the server.

                  const { data, isPending, refetch } = useQuery({
                        queryKey: ["todos", id],
                        queryFn: () => getTodos(id),
                        staleTime: 500000,
                  });

            2) Query Invalidation : This is used when you have made some changes to the data on the server (like added/ updated/ deleted some data) and now you want to refetch the data to get the updated data from the server. This is done using "useQueryClient" hook provided by TanStack Query. This will refetch the data no matter what the "staleTime" is set to.
                  Ex:
                        import { useQueryClient } from "@tanstack/react-query";

                        const queryClient = useQueryClient();

                        // After adding a new todo on the server
                        await addTodoOnServer(newTodo);
                        queryClient.invalidateQueries({ queryKey: ["<correct-queryKey-here>"] });

                  Note: invalidateQueries() technically returns a Promise that resolves when all the queries are refetched. So, if you want to wait for the refetch to complete before doing something else, you can await it.

            3) Mutation : This is used to make changes to the data on the server (like add/ update/ delete data). This is done using "useMutation" hook provided by TanStack Query.

                        import { useMutation } from "@tanstack/react-query";

                        const { mutate } = useMutation({ 
                              mutationFn: (<correct-input-here eg: newTodo>) => {
                                    // The actual mutation function that performs the mutation (e.g., creating, updating, or deleting data).
                              }, 
                              onMutate: (variables) => {
                                    // A function that executes before the actual mutation function (mutationFn) is fired. 
                                    return <old-data>;
                              },
                              onError: (error, variables, context) => {
                                    // Runs when an error happens!
                              },
                              onSuccess: (data, variables, context) => {
                                    // Runs when mutation is successful!
                              },
                              onSettled: (data, error, variables, context) => {
                                    // Error or success... doesn't matter! This always runs at the end.
                              },
                        })

                  Here: The different parameters in the callback functions above are:
                        (i) data: The data returned from the mutationFn after a successful mutation.
                        (ii) variables: This is whatever you passed to mutate() function when you called it. 
                              Ex: mutate(newTodo) --> here, "newTodo" is the "variables"
                        (iii) context: This is whatever the onMutate function returned. You can use this to pass some data from onMutate to onError/ onSuccess/ onSettled functions. Here, it is "context.<old-data>".
                              - This is useful for things like optimistic updates, where you want to update the UI immediately before the mutation completes, and then revert if there’s an error. The flow goes like this:
                                    (i) in onMutate, get the old data from tanstack's cache
                                    (ii) update the cache with optimistic data
                                    (iii) return the old data from onMutate as "context" so that it is available in onError
                                    (iv) in onError, revert the cache to old data using the "context" parameter
                              Eg:
                                    onMutate: async (newTodo) => {
                                          const previousTodos = queryClient.getQueryData(["todos"]);

                                          // Optimistically update to the new value
                                          queryClient.setQueryData(["todos"], (oldTodos) => [
                                                ...oldTodos,
                                                newTodo,
                                          ]);

                                          return { previousTodos };
                                    },
                                    onError: (error, newTodo, context) => {
                                          queryClient.setQueryData(["todos"], context.previousTodos);
                                    },
            
            ✏️TLDR: useQuery is for getting the data from the server, useMutation is for changing the data on the server!

            4) Dynamic Queries: It is just a way to define your queryOptions in a separate file and not directly in the useQuery hook. The video explains it in great detail in hwo to write a very clean dynamic queryOptions file in TypeScript. Watch the video for the template if needed. (from 29:50 onwards)

            5) Infinite Querying: When a backend endpoint can possibly return a large list of items, it’s common to split the results into pages and load them one at a time. This is called "pagination". 

                  📒Note: - It is the backend endpoint's responsibility to support pagination in the first place. 
                          - IF the backend endpoint supports pagination, TanStack Query provides a special hook called "useInfiniteQuery" to implement infinite querying in the frontend.
                              Ex: Page 1: items 1-10
                                  Page 2: items 11-20
                                  Page 3: items 21-30
                                  and so on...

            6) prefetching queries: You can prefetch queries using the "queryClient.prefetchQuery" method. This is useful when you want to load data in the background before it’s needed to simulate faster load times for the user.
                  Ex: fetching the data when mouse enters a button rather than when the button is clicked. Based on the assumption that user will click the button if mouse enters it. 

                  const queryClient = useQueryClient();
                  const prefetchData = () => {
                        queryClient.prefetchQuery(getUserQueryOptions());
                  }

                  <button onMouseEnter={prefetchData} >
                        Click Me to get User Data
                  </button>

            1) Node: A node is typically a server — physical or virtual — running MinIO.

            2) Drive: A drive is an individual storage device on that node.
                  HDD, SSD, mounted volume — doesn’t matter

            3) Availability: Can the system stay up and serve data if something fails?

      1) MinIO Deployment Types
            1) Single Node Single Drive (One machine, one disk.)
                  Supports Versioning and Object Retention (Locking)
                  No availability or redundancy outside of what the disk provides
                  Losing the disk or node results in downtime or data loss
            
            2) Single Node Multi Drive (One machine, multiple disks (e.g., /mnt/d1, /mnt/d2, /mnt/d3))
                  Supports all MinIO Features (Versioning, Locking, Replication, Expansion)
                  Drive-level redundancy and availability only
                  Losing the node results in downtime or data loss

            3) Distributed: Multi Node Multi Drive (Many machines, each with one or more disks)
                  Supports all MinIO Features (Versioning, Locking, Replication, Expansion)
                  Node and Drive level redundancy
                  Can tolerate loss of up to half the nodes or drives in the deployment
                  
                  This is where things like "Load Balancers" come up.

      0) What is Redis: Open source, in memory data-store (can be used for multiple things like cache etc.)
      1) Why Redis:
            Consider this scenario: You have a website with frontend + server (backend) + database. A user visits the site. The frontend sends an API request to fetch details from the backend.  
                  The backend queries the database and gathers the data. Suppose the data is "computed" from various tables:  
                  - Profile info from one table  
                  - Some ID from another table  
                  - Friends list or connections from yet another table  
                  (Think of Instagram: profile picture, unread messages, friend requests, etc.)  
                  Basically, this is an expensive query.

            Now, the user receives this "computed data" on the frontend.  
            If the user refreshes the page, all that work happens again!

            Problems:
            i) Re-querying and recomputing data across multiple tables  
            ii) High response time (poor user experience on refresh)  
            iii) High cost (too many expensive reads from the database)

            Enter Redis 🔴:
                  You create a Redis server, which runs in RAM (so Redis is running in RAM).  
                  Initially, Redis has no data. On the first request by a user, the backend fetches data from the database and also stores this "computed" data in Redis (here, Redis is acting as a cache).  
                  On subsequent requests, there is no need to query the database again. The data can be directly read from Redis.

            What is Computed Data?  
                  Consider something that is a dependent attribute, like age (which can be derived from date of birth), or something else that is not directly stored but can be computed using queries.  
                  We can directly save this computed data in Redis because recomputation every time is expensive.

            📒 Layer Caching in Docker: 
                  nDocker uses caching, so the order of commands in the Dockerfile is very important.

                  Case 0:  
                        If you don’t make any changes in the code and just rebuild the image, it will be lightning fast because Docker has everything cached and it knows there were no changes.

                  Case 1 (Good):  
                        Since the lines referring to our code are placed after installing Node.js, when we change our code and rebuild the Docker image, Docker already has everything up to "RUN apt-get install -y nodejs" cached.  
                        This means that part executes very fast, and only the code-related lines are processed again.  

                        Example:

                        FROM ubuntu  
                        RUN apt-get update  
                        RUN apt-get install -y curl  
                        RUN curl -sL https://deb.nodesource.com/setup_18.x | bash -  
                        RUN apt-get upgrade -y  
                        RUN apt-get install -y nodejs  

                        COPY package.json package.json  
                        COPY package-lock.json package-lock.json  
                        COPY main.js main.js  

                        RUN npm install  
                        ENTRYPOINT [ "node", "main.js" ]  

                  Case 2 (Poor):  
                        If the code lines appear first, then whenever we change the code, those lines will be processed again, but also everything after them (like installing Node.js).

      1) Problem: How does a simple HTTP connection work?  
            The client sends a request to the server, the server sends back a response, and the connection is closed.  
            If the client sends another request, the server responds and the connection is closed again.  

            Now, consider building a real-time chat application with 2 clients and 1 server.  
            Client 1 can send a message for Client 2 to the server. But how will the server deliver it to Client 2?  

            1) Method 1 (Polling):  
                  Client 2 asks the server every 1 second if there is a new message.  
                  The problem is that with thousands of clients, this creates unnecessary overhead for the server.

            2)  Method 2 (WebSocket Connection):  
                  Here, the client sends the server a simple HTTP request, but with an Upgrade header asking the server to upgrade this connection to a WebSocket connection.  
                  The server accepts, and now the connection does not close.  
                  At this point, there is a bidirectional connection between the client and the server, so either side can send messages to the other.

      3) Using Socket.IO
            1) In backend server (see "BackEnd/SocketIO/server.js")

            2) On frontend (See "BackEnd/SocketIO/public/index.html") :
                  (i) Now on the server we have installed Socket.IO npm package but what about frontend. Well, we will add this line in our frontend code: 

                      <script src="/socket.io/socket.io.js"></script>

                  - What this will do is get a script (Since src is "/socket.io/socket.io.js", it is requesting the script from the same url that loaded it i.e our backend). 
                  - The Socket.io code in our "BackEnd/SocketIO/server.js" is reponsible for sending this script.

      4) Rooms in Socket.IO: using .emit() from the server will send the message to all the sockets. What if we want to:
            (i) Send a message to only some sockets from the server?
            (ii) Or, what if we want some clients to join a room and then all the clients in that room only are connected with each other.
      In this case, we use Rooms.

            1) What is a Room: a Room is just something with a unique name. So, to make a room, you just have to have a unique name. Then everyone in that room will only talk to each other.
            
                  🔴Tip: By default, every client has a "unique" socket ID, so every client is initially in a room of its own (with the  same name as its socket ID). You can use a clients socket ID to do (i) and (ii) above in 4)

                  (See entire code in Corresponding Folder)
                  (i) To send a message to a specific socket: socket.to(<specific_socket_id>).emit(...);
                  (ii) To join a room: socket.join(room_id);
      
      5) emit callbacks in SocketIO: Really cool stuff, this let's you call a function (called the "emit callback" function) from the server on the client [So, basically, you are calling code from the server on the client- something you can't do otherwise but can here because this is a WebSocket connection underneath SocketIO]
            // client Code
            socket.emit("join-room", room_id, <callback-here>);
            📒Note: The callback should be the last parameter in the .emit() call

            // Server Code
            socket.on("<socket-event-name>", (<other-things>, <callback_from_client>) => {
                  socket.join(room_id);
                  <callback_from_client()>; # We are calling the callback received from the client here, it's code will be executed on the client!
            })

      6) Namespaces in SocketIO: Can be used to separate connections say all users on "/" namespace and all admins on "/admin" namespace. Each namespace has it's own: event handlers, rooms and middlewares.

      (i) Possible use cases: You want to create a special namespace that only authorized users have access to, so the logic related to those users is separated from the rest of the application

      7) Connecting and Disconecting a SocketIO connection 
            (i) <socket>.emit(...) : will store all messages if you are not connected to the server and send them when the connection is backup
            (ii) <socket>.volatile.emit(...) : will just forget the message if you can't send it right now!

            4) Dependency injection in FastAPI (See "BackEnd/fastAPI/main.py"):
                  1) creating a session object, then running the route handler, then closing the connection as in:

                        @app.get("/products")
                        def get_all_products():
                              db = session()
                                    ...
                              db.close()
                              return products

                        is very repetitive when done for all the route handlers. 
                  2) Rather we can use dependency injection provided by fastAPI as follows:

                        def get_db():
                              db = session()
                              try:
                                    yield db
                              finally:
                                    db.close()

                        @app.get("/products")
                        def get_all_products(db: Session = Depends(get_db)):
                              # Query the DB
                              db_products = db.query(database_models.Product).all()
                              return db_products

                        (i) Here, "db: Session = Depends(get_db)" says that "get_all_products()" function needs the "db" object to run from the "get_db()" function.
                        (ii) Also, the way dependency injection works in fastAPI, "get_db()" will "yield" the db object to  "get_all_products()" and stop there. Once  "get_all_products()" is done i.e the request has been served, "get_db()" will run from after the "yield db" line and ultimately, the "db.close()" will run. [You can read up on how the "yield" keyword works in python and how fastAPI uses it.]
                        (iii) So, why try-finally, why not just:

                              def get_db():
                                    db = session()
                                    yield db
                                    db.close()

                              Well, it works fine if everything goes good in the route handler i.e "get_all_products()". But if an exception arises in the route handler, "db.close()" would never run -> Connection leak 💀

            This will create "BackEnd/fastAPI/myapp/versions/de1bb338be87_create_user_table.py" file:

                  🔴Tip: Alembic migration v/s revision:
                        - revision : A revision, in Alembic, refers to a specific, version-controlled change to your database schema. Each revision is represented by a unique Python script file generated by Alembic (e.g., ~/versions/abcdef12345_create_user_table.py). This file contains both an upgrade() function, which defines how to apply the schema change, and a downgrade() function, which defines how to reverse it. Revisions are essentially the individual units of change that Alembic tracks, similar to commits in a version control system like Git.
                        - migration : A migration, in the context of Alembic, refers to the process of applying one or more revisions to your database. When you run "alembic upgrade head", you are performing a migration that applies all pending revisions to bring your database schema up to the latest version. Similarly, alembic downgrade performs a migration to revert changes by applying the downgrade() functions of specific revisions.

                  (i) down_revision : this will point to the previous revision. For the 1st revision, it will be "None".
                  (ii) upgrade() / downgrade() functions: You can write code in these to tell alembic how to revert to the previous revision (for downgrade()), similarly for upgrade(). Later, we will use sqlalchemy to autogenerate this code but for now, let's code it ourselves.
            2) - alembic upgrade <revision-id> : to apply a particular revision. 
               - alembic upgrade head : to apply the most recent revision. 
            3) - alembic history : to see all the revisions you have applied using alembic till now.
               - alembic current : to get the current revision you are on (more precisely - the unique hash of the current revision)
            4) downgrading alembic revision: 
                  (i) relative migration : operate relative to the current revision
                        - alembic downgrade -1 : This will downgrade 1 revision back relative to the current revision
                        - alembic downgrade +1 : This will upgrade 1 revision forward relative to the current revision
                        - alembic downgrade base :  completely revert all revisions and go back to original state of the DB 

      4) How to autogenerate migrations from SQLAlchemy models : So, we don't want to manually write the revisions (i.e the upgrade(), downgrade() functions), we want it such that when we change a SQLAlchemy model and run a command, it is automatically detected by Alembic what changed and a suitable revision generated and it's migration applied.
            (i) We have to tell alembic where our ORM models are. For this do: (See "~/myapp/env.py" file) (Official Docs: https://alembic.sqlalchemy.org/en/latest/autogenerate.html#auto-generating-migrations) 

                  from <your sqlalchemy module here that has the "Base"> import Base
                  target_metadata = Base.metadata
                              
            (ii) Now run : alembic revision --autogenerate -m "<your revision message>"
            Then run : alembic upgrade head

      16) Intersection of Types in TS: An intersection type combines multiple types into one with the & operator. The resulting intersection type satisfies all the component types simultaneously.

            type Point2D = {
                  x: number;
                  y: number;
            };

            type pointOnZAxis = {
                  z: number;
            }

            type Point3D = Point2D & pointOnZAxis;

            // Equivalent to:
            // type Point3D = {
            //   x: number;
            //   y: number;
            //   z: number;

            📒Note: Now you know 2 operators you can use on types: unions (|) and intersections (&)
      
      17) The Never Type: In TypeScript, the "never" type represents values that can't occur. More ob this in the video but I am skipping it for now.

            📒Note: Intersecting Incompatible Types
            When you intersect two types that have incompatible fields, the result is the "never" type. For example:

            type Saiyan = {
                  name: "goku" | "vegeta";
                  powerLevel: number;
            };

            type Human = {
                  name: "krillin" | "yamcha";
                  age: number;
            };

            type SaiyanHuman = Saiyan & Human; // "SaiyanHuman" becomes "never" type

            Now the name property can't possibly satisfy both! Humans must be krillin or yamcha, and Saiyans must be goku or vegeta. So, the name property in SaiyanHuman becomes "never", which in turn makes the entire SaiyanHuman type "never".

      18) Interface VS Types in TS: As it turns out, there are two ways to define object types: the "type" keyword (as we've seen with type aliases) and "interfaces". Both are similar, but there are some differences.

            1) Interfaces can be extended using the "extends" keyword, allowing you to create new interfaces based on existing ones. Type aliases can achieve similar behavior using intersections (&).

            2) Declaration Merging: One unique feature of interfaces is declaration merging. If you declare the same interface multiple times, TypeScript merges them into a single interface. This is not possible with type aliases; redeclaring a type alias with the same name will result in an error.

                  🔴Tip: Declaration Merging can also lead to nasty bugs, so most of the times, just use "type" instead of "interface"

            🍀 TLDR: Just use "type" and don’t use "interface"! 🤣🤣

      21) Non-null Assertion: It's common for TypeScript libraries to assume that a value can be null or undefined even when you know it can't be. You can assert that it's not with the non-null assertion (!) operator. It tells the compiler that a value cannot be null or undefined, even when the type system thinks it might be.

      Ex:
            interface User {
                  id: string;
                  name?: {
                        first: string;
                        last: string;
                  };

            sentText(user.name!.first);

      📒Note:  Only use non-null assertions when you're crazy-confident that the value can't be null or undefined. Just use a conditional guard clause if there is any uncertainty. This is always safer, albeit more verbose:

            function sendTextSafely(text: string | null) {
                  if (text === null) {
                        throw new Error("Text is required");
                  }
                  sendText(text);
            }

      23) Utility Types in TS: TS provides several built-in utility types to facilitate common type transformations. These help us to stick to "Single Source of Truth" principle. 
      Ex: Say you have an interface "User" with many properties and you want to create a new type where all properties are optional. Instead of redefining the entire interface with optional properties, you can use the "Partial" utility type.

            ❌❌BAD CODE❌❌
                  type User = {
                        id: number;
                        name: string;
                        email: string;
                  }

                  // Manually creating a type with all properties optional
                  type UserWithOptionalFields = {
                        id?: number;
                        name?: string;
                        email?: string;
                  }

                  This is bad because if you change the "User" type later, you have to remember to change "UserWithOptionalFields" too! Refactoring nightmare!
            ✅✅GOOD CODE✅✅
                  type User = {
                        id: number;
                        name: string;
                        email: string;
                  }
                  // Using Partial utility type
                  type UserWithOptionalFields = Partial<User>;

            1) Some commonly used utility types are: 
                  1) Partial<T>: Constructs a type with all properties of type "T" set to optional.
                  2) Required<T>: Constructs a type with all properties of type "T" set to required.
                  3) Readonly<T>: Constructs a type with all properties of type "T" set to readonly.
                  4) Pick<T, K>: Constructs a type by picking a set of properties K from type "T".
                  5) Omit<T, K>: Constructs a type by omitting a set of properties type "K" from type "T".
                  6) Record<K, T>: Constructs an object type whose property keys are type "K" and property values are type "T".
      
      24) Generics in TS: Allow you to create reusable logic that works with many types rather than a single one. Think of a data structure like a Queue or a Stack. They can hold any type of data, so it would be really annoying to reimplement them for every type:
            NumberQueue
            StringQueue
            UserQueue
            etc.
            
            Generics let us create a single Queue<T> type that can work with any type T

            1) "extends" keyword in Generics: You can use the "extends" keyword to constrain a generic type to a specific subset of types. This is useful when you want to ensure that the generic type has certain properties or methods.

                  Ex: 
                        type IHaveName = {
                            name: string;
                        }
                        // Below, T can be any type but should also satisfy "IHaveName" type (i.e should have a "name" of type "string").
                        function sayHi2<T extends IHaveName>(user: T){ 
                            console.log(`Hi ${user.name}`);
                        }

                        sayHi2({
                            name: "Geetansh Bhardwaj",
                            age: 20
                        })
                        // Output: Hi Geetansh Bhardwaj

            2) Type Parameters for Types: Type parameters aren't just limited to functions and methods! You can use type parameters to create generic types as well!
                  Ex: 
                        type Marks<T> = {
                            user_marks: T
                        }

                        let marks1: Marks<string> = {
                            user_marks: "100",
                        }
                        console.log(marks1.user_marks)
                        let marks2: Marks<number> = {
                            user_marks: 100,
                        }
                        console.log(marks2.user_marks)

            3) Conditional Types: these allow us to create new types based on conditions within the type system, they take this form (so you can only use the ternary operator here):

                  type NewType = SomeType extends OtherType ? TrueType : FalseType;

            Ex:
            type IsString<T> = T extends string ? true : false;

            // Usage
            type Result1 = IsString<"hello">; // true
            type Result2 = IsString<42>;      // false
            type Result3 = IsString<string>;  // true

      1) What is K8s: an open source container orchestration tool. Helps you manage containerized applications (docker or smthing else's containers) in different deployment environements (physical, virtual, cloud etc.)
      2) What problem does K8s solve:
            i) Earlier, applications used to be monoliths
            ii) But then, Microservice architecture came and apps would be split in 100s or 1000s of microservices. These microservices are separate and run in their own containers with independent updates, deployments etc. But managing 100s of containers individually is not easy, this is where K8s comes in!

      /******* Main K8s components *********/
            1) Node: This is a server
            2) Pod: this is an abstraction over a container. This is the smallest unit in K8s.
                  i) Why needed: when using K8s, you will only interact with K8s, no matter what container technology you are using (say, docker), so a Pod will run the container inside it.
                  ii) Usually, a pod is supposed to run just 1 container i.e 1 app in it (or maybe more supporting containers but 1 main container) like say an ExpressJS app.
                  iii) K8s provides a virtual network, so every pod gets an internal IP address (ofc its just within K8s). Different pods can communicate with each other using this IP (like an backend pod and a DB pod)
                  iv) Pods in K8s are ephemeral i.e can die if the app inside crashes or say the node running the pod ran out of resources. When that happens, a new pod is created in its place and gets a new IP address.

                  🔴Issue: if you are using IP addresses to communicate b/w pods, this would be an issue everytime a pod dies. For this see 3)
            3) Service: It is a permanent IP address. It can be attached to a pod. Lifecycle of Pod and Service are NOT connected, so even if pod dies, Service (and it's IP address) stays.
                  1) Types of Service:
                        i) external: a service that is open to requests from outside (say the frontend of ur app).
                              -It would accessible outside on a url like: http://<node ip>:<external service port>
                        ii) internal

            4) Ingress: You would not want a weird url for your external service (see 3) above), you would want it on a doamin name with https. For this we use Ingress.
                  - So, now, the request would go to ingres instead of the service and ingres would forward it to the relevant service.
            5) ConfigMap: Consider you have two services: one is an Express backend, and the other is a MongoDB database.

            Usually, you would have the database service URL hardcoded into your Express application. Now, if the name of the database service changes, you would need to:
                  - Update the code in the Express backend
                  - Push the changes to the repository
                  - Pull and redeploy it into the pod
            This becomes very tedious.

            This is where ConfigMaps come in: In a ConfigMap, you can define variables like the DB_URL. Whenever the service name changes, you only need to update the ConfigMap, without modifying or redeploying your application code.

            6) Secret: Sensitive data like database passwords is also part of external configuration, but it should never be stored in a ConfigMap, because ConfigMaps store data in plain text.

            Instead, such data should be stored in a Secret. Secrets store data in Base64-encoded format, providing a basic level of obfuscation.

            Just like ConfigMaps, pods can read data from Secrets and use it as needed (e.g., as environment variables etc).

            🔺Note🔺: Base64 encoding is not true encryption—it’s just encoding. For stronger security, additional measures (like encryption at rest and RBAC) are usually required.

            7) Volumes: Consider a pod running a database. If the pod restarts, all the data stored inside the container would be lost. We do not want that. To solve this, we use volumes.A volume can be attached to a pod, and it can refer to either:
                  - A local hard drive, or
                  - External storage outside the Kubernetes cluster (remote storage)
            This enables data persistence, meaning the data survives even if the pod restarts.

            Note: Storage is a separate layer from the Kubernetes cluster. Kubernetes itself does not fully manage data persistence—you need to handle it by configuring:
                  Volumes
                  Data replication
                  External storage systems etc.

            8) Deployment: Consider a pod my-app (say it is running an Express backend). If this pod dies, there will be downtime while a new one is being created. We want to avoid that.
            Assume this pod is exposed through a Service (S1). A Service provides a stable IP address and also acts as a load balancer.

            To prevent downtime, we run replica pods of my-app (often on different nodes). These replicas are also connected to the same Service (S1). The Service will route traffic to available/less busy pods, ensuring high availability.

            You don’t manually create these replica pods. Instead, you define a blueprint, for example:
            “I want 3 replicas of the my-app pod.”

            This blueprint is called a Deployment. It is a higher-level abstraction over pods, so in practice, you work with Deployments, not individual pods.

            💛 Note: 
                  1) A stateful pod cannot be replicated using a Deployment (i.e., one holding data). Simple replication in such cases is insufficient because it can lead to data inconsistencies. For example, different replicas might receive different write operations, which can cause conflicts or data mismatches.

                  So, Stateful applications require a specialized mechanism for replication.

                  2) 2) Deployment would also be used to scale up or scale down your application by defining how many replicas you want.

            9) StatefulSet: It provides a mechanism for managing stateful applications, especially databases like MongoDB, MySQL, and Elasticsearch. You should create such applications using a StatefulSet.

            Note: 1) A StatefulSet does not automatically eliminate data inconsistencies. Proper configuration of the database (replication, clustering, etc.) is still required to ensure consistency.
            2) Working with StatefulSets is generally more complex than working with Deployments. Because of this, it is a common practice to use Kubernetes mainly for stateless applications, and host databases outside the cluster (managed separately).

                  Scalability: being able to handle more requests
                        (i) Vertical Scaling: Buy Bigger Machine
                        (ii) Horizontal Scaling: Buy More Machines

                  | Feature                | Horizontal Scaling                                                                 | Vertical Scaling                                  |
                  |------------------------|------------------------------------------------------------------------------------|---------------------------------------------------|
                  | 1) Load Balancing      | Required                                                                           | Not required (single machine)                     |
                  | 2) Resilience          | If one machine fails, others can handle                                            | Single point of failure                           |
                  | 3) Communication       | Uses Network calls (RPC) for communication between machines (Slow)                 | Uses Inter-process Communication (IPC) (Fast)     |
                  | 4) Data Consistency    | Data consistency is challenging across distributed systems                         | Easy, as there is just a single machine           |
                  | 5) Scalability         | Scales well as users increase; linearly add more servers as users increase         | Hardware limitation; can't keep making machine bigger forever |

            /**** What are Database Indexes? ****/
                  - You have already done indexing in DB in your DBMS subject I guess (or maybe it was OS idk). It's that same thing, used to make queries fast in a DB. The concept is mostly the same in SQL and NoSQL DBs.

            /**** NoSQL DBs VS SQL DBs ****/
                  1) Advantages of NoSQL DBs/When You need NoSQL DBs:
                        i) SQL DBs have normalisation at heart, so something complex like address would be in a separate table with different columns like street, state, country etc. But, most of the times, all of this data is inserted and retrieved at once (inserted when user signs up, retrieved every time he opens his profile). So, why not store everything together? In a SQL DB, there would be a User table and a join with the Address table every time you want to get the user data, but in a NoSQL DB, you can just store everything together in one document and retrieve it in one go without any joins. So, NoSQL DBs are better when you have data that is mostly inserted and retrieved together.
                        
                        ii) Flexible Schema: NoSQL DBs are better when you have a lot of unstructured data.

                        iii) Horizontal Scalability: NoSQL DBs are designed to scale horizontally (something to do with - data in these can be easily stored in separate partitions). By doing this, NoSQL DBs prioritize availability (1 partition fails but others still up). So, NoSQL DBs allow "availability over consistency" (Why so is not fully clear yet to me, will come back to it later).

                  2) Disadvantages of NoSQL DBs:
                        i) Consistency Issues: NoSQL DBs often sacrifice consistency (differnet partitions show different data for same user_id). They work on the model of eventual consistency (which means that while they will eventually become consistent, there may be times when they are not). So:
                              - NoSQL don't guarantee ACID properties (C is for consistency). But SQL BDs do guarantee ACID properties.
                              - Thus, NoSQL DBs are not good if your app has too many Updates (Update = Delete + Insert) because of consistency issues. Different people will see different stuff - confusing 🫤. 

                        ii) NoSQL DBs are not read optimized. Say your document structure in NoSQL DB is like:
                              {
                                    id: 12321
                                    name: "Geetansh Bhardwaj",
                                    email: "a@b.com",
                                    password: "hashed_password",
                                    address: {
                                          street: "123 Main St",
                                          city: "Anytown",
                                    }
                                    age: 21
                              }

                        Now I write a query to get all the ages, the DB will have to read the entire document (and that too for all users) to get the age field, which is inefficient. In SQL DBs, you can just read the "age" column from the "users" table without having to read the entire row.

                        iii) Joins in NoSQL DBs are not efficient. In NoSQL, Joins are just read all the documents, get the relevant field and match. In SQL DBs, Joins are optimized and efficient.

                  Ref: https://takeuforward.org/operating-system/what-is-cache

                  1) The underlying principle of cache memory is the locality of reference, which can be divided into two types:

                        i) Spatial Locality: Refers to the tendency of the CPU to access adjacent memory locations. If a program accesses a memory location, it is likely to access neighboring locations in the near future.
                        ii) Temporal Locality: Refers to the tendency of the CPU to repeatedly access the same memory locations within a short time period. This indicates that recently accessed data is likely to be accessed again soon.
            
      /**** Module 2 : Load Balancing ****/
            /**** What is Load Balancing (LB) ****/
                  1) Goal: Distribute traffic across identical servers. 
                  - Mostly used with stateless systems (or atleast it is easier to implement with stateless systems) because in stateful systems.
                        Eg: Multiple servers S1, S2, S3, all are equivalent and any request can be served by any of them. So, we can easily distribute the load between them. 

                  Ways to implement Load Balancing:
                        1) Simple hashing ( Ref: https://youtu.be/K0Ta65OqQkY?si=2H3xDlREVXlMKNi0 ) : You have N servers. You also have a uniformly random hash function "H". Now, when a request comes in with id "id" (we are also assuming that the request ids are uniformly random) you would:
                              i) Hash the id: H(id) -> gives you a number
                              ii) Modulo the hash with N: H(id) mod N -> gives you a number between 0 and N-1 which is the server number you will route the request to.

                              - Now, imagine you were serving 100% requests and you have 4 servers. So right now, each server takes 25% requests. Now, say your app goes viral and load is increasing, you decide to add 1 more server (so now you have 5 servers).
                              So, each server now would server 20% of the requests. But, there is a huge problem! ‼️‼️
                              - Request Sticking: earlier, with 4 servers, say a request with id 123 always came to server no. 1, call it S1. So, instead of fetching the details for this id from DB, S1 cached the details of id 123. But now, after adding S5, id 123 is no longer coming to S1, maybe it now goes to S2. So, the cache of S1 for id 123 is completely useless. 
                                    i) Let's calculate how much request reassignemnt have happened after we added S5:
                                          +5% : S1 looses 5% of requests and now handles 20% (earlier it was ahndling 25%)
                                          +5% : S2 gets the lost ones of S1. S2 is not at 25% + 5% = 30%
                                          +10% : S2 looses 10% of requests and now handles 20% (earlier it was handling 30%)
                                          +10% : S3 gets the lost ones of S2. S3 is not at 25% + 10% = 35%
                                          +15% : S3 looses 15% of requests and now handles 20% (earlier it was handling 35%)
                                          +15% : S4 gets the lost ones of S3. S4 is not at 25% + 15% = 40%
                                          +20% : S4 looses 20% of requests and now handles 20% (earlier it was handling 40%)
                                          +20% : S5 gets the lost ones of S4. S5 is at 20% (earlier it was handling 0%)

                                          So, Total Request Reassignment = 5% + 5% + 10% + 10% + 15% + 15% + 20% + 20% = 100% (All requests are reassigned, which is really bad for cache performance)

                                          📕 Conclusion: Our "Simple hashing" method completely failed when system was scaled horizontally. Entire cache was rendered useless. We need a better strategy.

                        2) Consistent Hashing ( Ref: https://youtu.be/zaRkONvyGr8?si=jYjQFQQPKxxrPBJj ): To solve the above problem, we can use consistent hashing. Here is how it works:
                              i) Earlier, in "Simple hashing", we took modulo with M (where M = N = no. of servers). 
                              Now, M = a very large constant number (say 2^32). We will take modulo with M instead of N. M = size of hash space.

                              You can imagine the entire hash space as a circle where 0 and M-1 are adjacent. Now, we will hash the servers as well. 

                              ii) Earler, only request ids were being hashed and modded. Now, each server will also be given an id, call it "sid". Now, this "sid" will also be hashed using the same hash function "H" and modded with M to get a point on the circle. So, we will have points on the circle for each server. Now, when a request comes in, we hash it and get a point on the circle. We will route the request to the first server that comes after this point in the clockwise direction.
                              
                              iii) In this way, even when new servers are added, only a small portion of the requests will be reassigned to different servers, thus improving cache performance significantly.

                              iv) Theoretically, the "Load Factor" = 1/N. But consider the event that a server fails, so all its request would go to the next server, say S, in the ring, potentially increasing the load on that by a huge amount. 
                              
                              To solve this problem, we can use "Virtual Nodes". Here, instead of hashing each server once, we hash it multiple times to get multiple points on the circle for each server. So, if a server fails, its load will be distributed among multiple servers in the ring, thus preventing any single server from being overwhelmed. There are 2 ways of implementing this:
                                    1) Use K different hash functions to hash each server K times. So, you will have K points on the circle for each server.
                                    2) Use a single hash function but concatenate the server id with a number from 1 to K to get K different inputs for the hash function. So, you will have K points on the circle for each server.

                                    🟨 Note: "2)" is better and is used in practice because designing K hash functions while maintaining random uniformity and consistency is hard. Generating K replica ids is easy: xxx gives K replicas xxx + '1', xxx + '2', ..., xxx + 'K'. Then you take these replicas and generate K points on the ring with the same hash function.

            /**** What is Sharding ****/
                  1) Goal: Distribute data across machines.
                        - Each shard holds a subset of the data.
                        - A request must go to the correct shard.
                        - Shards are not interchangeable.

                  🟨 Note: a DB is not a stateFUL system, so applying load balancing (LB) is difficult. For reads only you may apply LB. But for writes, their are consistency issues. Say user id 123 writes to DB1 but these writes now need to propagate to DB2, DB3 (assuming you have multiple replicas of the DB as DB1, DB2 etc and are LB b/w them).

                  2) 2 types of Sharding:
                        i) Horizontal Sharding: Distributing data across multiple servers/shards (Database servers) based on a shard key. So, it's partitioning based on rows.
                        ii) Vertical Sharding: Distributing data across multiple shards based on columns.

                  3) Key problems to consider:
                        i) Cross-shard Joins: very expensive
                        ii) Inflexibility/ Fixed no. of shards: Once you have a shard, say S, it is fixed. Now say this shard had data for user ids 1-100. Now say these users are very active and generating a lot of load, but the users in shard S2 (with user ids 101-200) are not generating much load. So, you want to move some users from S to S2 to balance the load, but that is really difficult because of all the changes in routing logic, data movement etc.
                        
                              Solution: 1) Consistent hashing. It is implemented in an in-memory DB called "memcached".
                                        2) Hierarchial Sharding: Here, every shard is further broken down into "mini-shards" and there is a shard manager per shard that keeps track of which mini-shard has which data.

                        iii) What happens if a shard fails?
                              Solution: 1) Master-slave architecture: 1 Master and multiple slaves copying him. Whenever there is a write, it goes to the master and then propagates to the slaves. Read requests can go to any of the slaves. 
                              
                              - If master fails, one of the slaves can be promoted to master and we are good to go. So we have good single point of failure handling here.

            /**** What is Bloom Filter ****/
                  Ref: https://youtu.be/bgzUdBVr5tE?si=7BnsXh7WOGDjBvTG

                  1) General Idea: Say you want to compare two strings for equality. The naive way is O(m+n). Even datastructures like Tries are there which have theoretically great complexity but not that great in practice. Rather, consider this idea:
                        - Say the two strings to be compared are X and Y. Now, we will have 3 hash functions H1, H2, H3. 
                        - We will hash X with these 3 hash functions to get 3 hash values: H1(X), H2(X), H3(X). 
                        - So, for us, X is represented by these 3 hash values i.e X = (H1(X), H2(X), H3(X))
                        - Similarly, we will hash Y with the same 3 hash functions to get Y = (H1(Y), H2(Y), H3(Y))
                        - Now, if X and Y are equal, there is very high PROBABILITY that (H1(X), H2(X), H3(X)) = (H1(Y), H2(Y), H3(Y)). So, we can compare the hash values instead of the strings. This is the basic idea behind Bloom Filters.

                  2) Bloom Filter Datastructure: The array based implementation you can see from the Ref. Key things to remember:
                        i) Bloom Filters can guarantee that the string has not been searched before
                        ii) Bloom Filters cannot guarantee that the string has been searched before (because of hash collisions).
                        iii)  Let:
                                    • m = number of bits in the Bloom filter
                                    • k = number of hash functions you pass a string through
                                    • n = number of inserted elements (here, inserted strings)

                              Probability a specific bit is not set to 1 after all n inserts
                                    For one hash of one element, prob a given bit is not set to 1: 1 - 1/m.
                                    For k hashes of one element: (1−1/m)^k 
                                    For n elements (k hashes each): P(bit is 0) = (1−1/m)^(kn) 
                                    So: P(bit is 1) = 1−(1−1/m)^(kn) 
                              
                              Now, false positive probability for a bloom filter i.e the probability that bloom filter says "string is present" when it is actually not present:
                                    - For a query string not in the set, it will be reported “present” if all k hashed bit positions are 1 for this string: 
                                          P(false positive) = (P(bit is 1))^k = [1−(1−1/m)^(kn)]^k 

                                    🟨 Final expression to remember: P(false positive for a string in bloom filter) = [1−(1−1/m)^(kn)]^k 
                                    🟨 From the above expression, if:
                                          i) If m --> ∞, P(false positive) --> 0
                                          ii) If m --> 1, P(false positive) --> 1
                                    🟨 If you graph the P(false positive) against k, it will not decrease forever as you increase k, rather there is an optimal value of k (you can derive that by differentiating the expression with respect to k) which is:
                                          k = (m/n) * ln(2)

            /**** What is Data Replication ****/

                  1) You don't always want just 1 DB, that is a single point of failure. So, you want to have multiple replicas of the DB. This is called data replication. Two strategies to attain it:    
                        i) Synchronus replication: Flow goes like this:
                              - Client sends a write request to the primary DB.
                              - The primary DB processes the write and updates its data.
                              - The primary DB then sends the write to the replicas (secondary DBs).
                              - The replicas acknowledge the write back to the primary DB.
                              - The primary DB waits for acknowledgments from all replicas before confirming the write to the client.
                        
                        This ensures consistency. Once client gets ACK, even if primary DB fails, replicas have the data.

                        Now, There are 2 options in ii):
                              a) Master - Slave architecture: Just like described above, 1 master and multiple slaves. Slaves can not accept writes, they just copy the master. But you have single point of failure here - the master.

                              b) master - master architecture: Here, all DBs are equal, they can all accept writes and they replicate to each other to stay in sync. 
                                    - No single point of failure here, if one master fails, all servers will start writing to the remaining masters.

                                    ‼️ Split brain problem: Say you have 2 masters M1 and M2. Now, say M1 and M2 lose connection with each other but are still up (say the router b/w them failed). Now both will accept writes but no syncing and you will have inconsistent data b/w them. 
                                          Ex: a client has $100 in account, he withdraws $90 from M1 and $90 from M2, overall withdrawing $180 from an account with just $100!

                                    ✅ Solution: 
                                          i) This problem can be solved with 3 master nodes instead of 2, all connected to all and a very UNREALISTIC assumption: It is impossible for a node to fail and also the connection b/w the other 2 nodes to fail at the same time. (See dig. in video). 

                              🟨 Some algorithms to keep in mind you have distributed systems:
                                    1) Case 1 - Distributed Consensus Problem: You have multiple masters, each receiving conflicting updates and now you need to agree on a single source of truth. 
                                          - Algorithms to solve: Paxos, Raft, BFT (Byzantine Fault Tolerance) etc.

                                    2) Case 2 - Distributed transaction: You have different DBs ( or different shards ) say DB1, DB2 etc. These store different data and are NOT replicas of each other. Now, you have a transaction that is distributed like:
                                          i) Step 1 in DB1
                                          ii) Then step 2 in DB2
                                          iii) Then step 3 in DB3

                                          and then the transaction is successful. So, if the step 3 in Db 3 fails, the entire transaction fails and you need to rollback the changes in DB1 and DB2 as well. So, you need a distributed transaction protocol to handle this. 
                                                - Algorithms to solve: 2PC (Two Phase Commit), 3PC (Three Phase Commit) etc.

                                    3) Case 3 - How to handle multiple transactions inside ONE DB concurrently: You have multiple transactions coming in concurrently to a DB. Now, you need to make sure that the transactions are executed in a way that they don't interfere with each other and the DB remains in a consistent state. 
                                          - Algorithms to solve: MVCC (Multi Version Concurrency Control) etc.

                        ii) Asynchronous replication: Flow goes like this:
                              - Client sends a write request to the primary DB.
                              - The primary DB processes the write and updates its data.
                              - The primary DB then sends the write to the replicas (secondary DBs).
                              - The primary DB does not wait for acknowledgments from the replicas before confirming the write to the client.
                        
                        This ensures lower latency but can lead to inconsistent data if the primary DB fails before replicas are updated. So now the client gets ACK but update is lost because replicas don't have it yet.

            /**** How are NoSQL databases optimized? ****/
                  1) So you have a client, a server and a DB. Client sends a request to server which then sends to DB and the DB sends acknowledgement back to the server. 
                 
                  🟥 Question: How do you scale it?
                        i) Every call from server to DB and back is a network call which includes headers and data from the server + acknowledgement (ack) from the DB. So, we can:
                              
                              🟩 Ans 1: Condense data queries into a single query: Send more data in a single query and get 1 ack back from the server.

                        ii) Let's focus on the DB. There are a lot of read-writes happening there. Can we optimize that? We have two options:
                              a) B+ Tree: Read: O(log n), Write: O(log n)
                              b) Log DataStructure (just like a Linked List): Read: O(n), Write: O(1): Nah! we can't have that slow reads

                        🟩 Ans 2: LSM tree (Log-Structured Merge Tree)
                              c) Log DataStructure (just like a Linked List) + Sorted array: Write: O(1) (write to Log), Read: O(log n) (binary search on sorted array)
                                    - This seems good but we would also need to factor in the complexity of converting the Log to a sorted array, where should we do this, definitely not on server bcz the whole point is to get O(1) writes. On the DB then. The entire flow would be:
                                          i) Client sends request to say add new Data X to server
                                          ii) Server appends X to Log in Server (O(1)). Server keeps appending to Log until it reaches a certain size. Once it reaches that size, the new data is sent in one request to the DB (thus following 🟩 Ans 1 as well) and the Log is cleared. 
                                          iii) The DB now receives the new data and sorts it. 
                                                Note: a) Say earlier the data in DB was: 3, 10, 12, 20....(1000 entries) 
                                                      b) Now the Log comes as: 2, 15, 18 (only 3 entries)
                                                      c) Now, the DB will not merge the Log with the sorted array! This would be inefficient as the DB would have to sort 1003 entries just because 3 new data came in. Instead it would just sort this and keep it as separate chunk. So we now have sorted chunks:
                                                            - Sorted Array 1: 3, 10, 12, 20....(1000 entries)
                                                            - Sorted Array 2: 2, 15, 18 (only 3 entries)
                                          iv) When a read request comes in, the DB will do binary search on all the sorted chunks and get the result. So, the read complexity is O(K log n) where K is the number of sorted chunks. The data would be found in one of the chunks.

                                          📒Note: If there are a high number of sorted chunks, that too is a problem. So we can use a hybrid aproach of cleverly merging some of the chunks as long as the operation of merging itself is not too expensive. There can also be other add-ons like using bloom filter per chunk to check whether a data value is present in a chunk or not before trying to search the chunk.
                                    
                                    🟧 1) General idea to takeaway for LSM trees: You want fast writes so use Log datastructure. But then reads would be too slow so you also keep sorted chunks.
                                       2) Key terms: i) Sorted String Table (SSTable): the sorted chunks in the DB. 
                                                     ii) Compaction: the process of merging the sorted chunks in the DB to keep the number of chunks manageable.

      /********** 1. Introduction to LLD ***********/
            /********** 1.1 Introduction to Low Level Design ***********/
                  1) Why LLD: when code base grows, if you have not followed some design principles while writing it, it would be difficult for you to navigate, maintain and change it. So, LLD is needed for you when writing code to ensure your codebase is maintainable and scalable.
                  2) LLD Formal Definition: It is when your code starts to take shape. It is the bridge b/w architecture and implementation. 
                        Eg: Authentication is to be implemented. When you start thinking about which class, objects, interfaces I would make for this, that is LLD

                        So, LLD is when you are getting into the details of the code and applying OOPs principles.
            
            /********** 1.2 Software Design Principles ***********/
                  1) DRY (Do Not Repeat Yourself): each piece of knowledge/logic should have a single, unambiguous representation within the system.  
                        1) When not to use DRY/ when can you skip DRY:
                              i) Premature Abstraction: Premature abstraction is a software development error where developers generalize code, introduce interfaces, or create complex abstractions too early, often based on assumed future needs rather than actual, present requirements. This over-engineering increases system complexity, hinders readability, and makes future changes harder.
                              ii) performance critical code: if something critical is working fine, maybe not touch it for now. :)
                              iii) Legacy code can be left untouched if it's working fine and no one understands properly how it works
                              iv) Don't Sacrifice readability with too much DRY by over abstracting everything.

                  2) KISS (Keep It Simple, Stupid): A design should be kept as simple as possible. Complexity should be introduced when absolutely necessary.
                  3) YAGNI (You Aren't Gonna Need It): Always implement things when you actually need them, never when you just forsee that you might need them.

      /********** 2. Solid Principles ***********/
                  1) This is a group of 5 principles

                  /********** 2.1 Single Responsibility Principle (SRP) ***********/
                        1) Definition: A class should have only one reason to change. So, a class should have only one job, one responsibility, one purpose.
                              - If a class takes more than one responsibility then those responsibilities become coupled and changes to one might break the other.

                        Note: SRP is not only for classes, it can be for functions, microservices etc.

                  /********** 2.2 Open Closed Principle (OCP) ***********/
                        1) Definition: Software entities (classes, modules & functions) should be open for extension but closed for modification.
                              - Say class X is being used at 5 places, if u modify it, it would break at other places. So, no modification but ppl can extend it if they want a change.

                  /********** 2.3 Liskov Substitution Principle (LSP) ***********/
                        1) Definition: If S is a subtype of T, then objects of T may be replaced with objects of S without altering any of the desirable properties of that program.
                              - Simpler version: If class B is a subclass of class A then you should be able to use B anywhere you used A, and the behaviour should remain correct.

                        2) What happens when your code violates LSP?:
                              i) Broken functionality when subclass replaces parent class
                              Ex:
                              class Notification{
                                    public void sendNotification(){
                                          System.out.println("Email Notification Sent");
                                    }
                              }

                              class TextNotification extends Notification {
                                    @Override
                                    public void sendNotification() {
                                          // This is violation of LSP, the new subclass has changed the behavior of old class. Behavior should not have changed.
                                          throw new RuntimeException("Not supported");
                                    }
                              }

                              public class Main {
                                    public static void main(String[] args) {
                                          
                                          // Old way: Email Notification
                                          // Notification notification = new Notification(); 
                                          
                                          // New way: we want text notification now.
                                          Notification notification = new TextNotification(); // Trying to use LSP
                                          notification.sendNotification();
                                    }
                              }

                        3) In a nutshell: LSP says subclass should extend the behavious of the base class not change it.

                        4) Key Principles of LSP:
                              1) Design by contract (From chatGPT)
                                    Each class has a contract — rules it must follow:
                                          - Preconditions → what must be true before a method runs
                                          - Postconditions → what the method guarantees after running
                                          - Invariants → conditions that always remain true

                                    When a subclass extends a parent class:
                                          It must not make stricter preconditions (can’t demand more)
                                          It must not weaken postconditions (can’t guarantee less)

                                    Why for LSP?
                                    If a subclass breaks this contract, it can’t safely replace the parent.

                                    Example:
                                          Parent: withdraw(amount) allows any amount ≤ balance
                                          Child: only allows withdrawals on weekdays ❌
                                          → This breaks expectations → violates LSP

                              2) Use Composition (From chatGPT)
                                    Instead of inheriting (IS-A relationship), build classes using other classes (HAS-A relationship).

                                    Inheritance (bad in some LSP cases):
                                          Child automatically inherits behavior
                                          May be forced to override methods incorrectly → breaks LSP

                                    Composition (better alternative):
                                          You delegate behavior to another class
                                          No need to pretend to be something you’re not

                                    Example:
                                          1) Inheritance ( Leads to problems ❌❌  )
                                          class Bird {
                                                void fly() {
                                                      System.out.println("Flying...");
                                                }
                                          }

                                          class Penguin extends Bird {
                                                @Override
                                                void fly() {
                                                      throw new UnsupportedOperationException("Penguins can't fly");
                                                }
                                          }

                                          ❌ Issue:
                                                Penguin is-a Bird, but can’t behave like one
                                                Breaks Liskov Substitution Principle (LSP)
                                                If someone uses Bird b = new Penguin(); b.fly(); → 💥 crash

                                          2) Composition (HAS-A instead of IS-A ✅✅ )  
                                          Step 1: Create behavior interface
                                                interface FlyBehavior {
                                                      void fly();
                                                }

                                          Step 2: Different implementations
                                                class CanFly implements FlyBehavior {
                                                      public void fly() {
                                                            System.out.println("Flying...");
                                                      }
                                                }

                                                class CannotFly implements FlyBehavior {
                                                      public void fly() {
                                                            System.out.println("Cannot fly");
                                                      }
                                                }

                                          Step 3: Use composition in Bird
                                                class Bird {
                                                      private FlyBehavior flyBehavior;

                                                      Bird(FlyBehavior flyBehavior) {
                                                            this.flyBehavior = flyBehavior;
                                                      }

                                                      void performFly() {
                                                            flyBehavior.fly();
                                                      }
                                                }

                                          Step 4: Create birds
                                                public class Main {
                                                      public static void main(String[] args) {
                                                            Bird sparrow = new Bird(new CanFly());
                                                            Bird penguin = new Bird(new CannotFly());

                                                            sparrow.performFly();  // Flying...
                                                            penguin.performFly();  // Cannot fly
                                                      }
                                                }

                                          ✅ Why this works
                                                No fake inheritance
                                                No overriding to “break” behavior
                                                Each object gets the right capability

                  /********** 2.4 Interface Segregation Principle (ISP) ***********/
                        1) Definition: Clients should not be forced to depend on interfaces they don't use.
                              - i.e Don't create large, bloated interfaces.
                              - Break them into smaller and more specific interfaces.
                        2) When to know that you need to implement ISP:
                              i) When ur interface is doiing too many things.
                              ii) When a class implementing an interface throws an error in one of the functions of the interface (like class says we don't want this function so throw error not supported): Now you know that interface has a function that the class does not want, so we can use ISP to simplify the interface.

            1) POM (page object model)
                  Without POM: page.getByRole(AriaRole.TEXTBOX, new Page.GetByRoleOptions().setName("Username")).fill("Admin");
                        - All things like:
                              i) object locator code
                              ii) testing code  
                              iii) Action methods (here, fill("Admin"))   
                        in same script.
                        - Unreadable, hard to maintain ( say "Username" becomes "Username123" in future, now we have to manually change at 50 different places throughout) 

                  With POM:
                        1) We have 2 separate things:
                              i) LoginPage.java : this will have "object locator code" + "Action methods"
                              ii) LoginTest.java : this will have "testing code"
                              
                              LoginTest.java will import necessary stuff from LoginPage.java
                        2) So, in POM, Every webpage = One class (e.g., LoginPage, HomePage) etc.
